# 08-1 · 真实模型：什么时候该接，怎么接

林澈的材料里只有一句「收藏了 Kubernetes 教程」，画像里却出现了 Kubernetes。先用默认 Demo 和两种导入方式重现这个现象，再顺着配置判断是哪一段程序或模型给出了结果。

只用浏览器可读配置和预期结果。跟做使用已启动的 Demo API、两个新教学账号和一份合成 JSON，无需 API Key。真实模型配置可选。阅读约 20 分钟，动手约 15 分钟。 [第一次跑起来](../01-第一次跑起来.md) · [证据判断](../00-foundations/00-2-提示词与证据.md)

**对应源码**：`backend/app/llm/provider.py`、`backend/app/core/config.py`、`.env.example`。

---

## 生成和检索各用一套配置

| 哪一层 | 默认练习会怎样 | 可选配置与要核对的结果 |
| --- | --- | --- |
| 生成 | Demo 使用确定性规则或模板，无需密钥 | DeepSeek、OpenAI 兼容服务或本机端点。核对实际 provider、模型名和回退状态 |
| 证据检索 | 第三、四章副本用本地评分。默认 Compose 有 Qdrant，默认配哈希向量和词法重排 | 也能单独给 Qdrant 选配 Qwen Embedding 和重排器，再检查候选与检索诊断 |
| 评测 | 可复跑固定样本 | 更换模型后，用相同的合成或获授权样本单独比较结果 |

**关键提醒**：默认链路的匹配分数是规则权重算出来的，不是录用概率，也不是「真实准确率」。接了真实模型也不代表效果自动变好——必须按[评测口径](08-2-评测.md)单独验收。

## 配置项各管什么

`.env.example` 里和模型相关的项：

| 配置 | 作用 | 默认 |
| --- | --- | --- |
| `AI_PROVIDER` | 生成模型来源 | `demo` |
| `AI_BASE_URL` | OpenAI 兼容端点地址 | `https://api.deepseek.com` |
| `AI_API_KEY` | 密钥 | 空 |
| `AI_MODEL` | 默认模型名 | `deepseek-flash` |
| `MODEL_ROLE_BINDINGS` | 按角色指定不同模型 | 空 |
| `RERANK_STAGES_ENABLED` | 是否开启两级重排 | `false` |
| `RERANK_COARSE_TOP_K` / `RERANK_FINE_TOP_K` | 粗排 / 精排条数 | 15 / 5 |

生成侧支持 `demo`、`deepseek`、`openai_compatible` 和 `local`。本机 Qwen 用于生成时，可以设 `AI_PROVIDER=local`，并填写支持该模型的 OpenAI 兼容端点。检索侧的 Qwen 则由 `RETRIEVAL_PROVIDER=qwen` 选择。

`MODEL_ROLE_BINDINGS` 的格式是 `answer=model-a,wiki=model-b,...`，可用角色有 `answer`、`wiki`、`analysis`、`profile`。不绑定的角色回退到 `AI_MODEL`。模型不可用时会自动回退到确定性结果，并在诊断里记录。

**先看源码再配**（`backend/app/llm/provider.py`）：

1. `get_llm_provider(role)` 按 `AI_PROVIDER` 选择生成实现。检索使用独立的 `get_embedding_provider()`，默认选 `hash-v1`，维度为 384。
2. `MODEL_ROLE_BINDINGS` 按角色解析，某角色没绑定时用 `AI_MODEL`。兼容 Provider 记录调用异常并抛回调用方，由 Copilot 或 Wiki 编译器决定回退并更新诊断。
3. 重排角色单独配：`RERANK_STAGES_ENABLED` 默认 `false`，只有开启后才是粗排 Top15 → 精排 Top5（`config.py:42-44`）。

### 选择链：用诊断确认实际 Provider

`_get_llm_provider_for`（`provider.py:162-179`）有一段静默降级逻辑，很值得亲手追一遍：

```python
ai_provider = settings.ai_provider.lower().strip()
if ai_provider == "demo" or (ai_provider == "deepseek" and not settings.ai_api_key):
    return DemoProvider()
if ai_provider not in {"deepseek", "openai_compatible", "local"}:
    return DemoProvider()
return OpenAICompatibleProvider(...)
```

三种情况会回到 Demo：**显式配了 `demo`**；**配了 `deepseek` 但 `AI_API_KEY` 是空的**；**配了一个不认识的值**（比如写错的 `qwen`）。后两种会直接选中 Demo。Copilot 的 `model.provider="demo"` 和 `model.model="deterministic"` 可确认实际实现。若调用真实 Provider 后出错，响应可以保留该 Provider 的名称，同时标 `fallback=true` 并提供原因。

还有个容易找错的地方：源码里**没有** `DeepSeekProvider` 或 `LocalProvider` 类。`deepseek`、`openai_compatible`、`local` 三种值都实例化同一个 `OpenAICompatibleProvider`，只是传进去的 `provider` 字符串不同——它们共用 OpenAI 兼容的 `/chat/completions` 协议，区别只在 base_url 和 model。真正不同的实现是 `DemoProvider`（`generate_json` 直接抛错，让上层走确定性回退）和 `OpenAICompatibleProvider`（真的发 HTTP 请求，带 `response_format=json_object`、`temperature=0.1`，用正则剥掉代码围栏后 `json.loads`）。

### 角色绑定：一次配置，四个角色各用各的模型

`MODEL_ROLE_BINDINGS` 的格式是 `answer=model-a,wiki=model-b,analysis=model-c,profile=model-d`，逗号分隔的 `role=model`。解析逻辑在 `config.py:82-95`：没有 `=` 的片段跳过，空 role/空 model 跳过，没绑定的角色回退到 `AI_MODEL`。

调用方按角色取 provider：`get_llm_provider("answer")`、`get_llm_provider("wiki")`、`get_llm_provider("profile")` 等。选择器上加了 `@lru_cache`，键是 `(role, model)`，所以不同角色即使绑同一个模型也互不干扰。**无参调用默认 `answer` 角色**——老代码 `get_llm_provider()` 仍然能跑。

这套设计的实际价值：Wiki 编译和画像提取可以各用擅长的模型，而回答用另一个。但如果某个角色的模型挂了，`OpenAICompatibleProvider` 会记录失败并让上层回退到确定性结果，`fallback` 诊断会变 `true`——所以「四个角色都配了模型」也不代表每次调用都成功用上了模型。

### 真实生成、向量召回与重排

这是最容易配错的地方。项目里有两个独立的 `*_PROVIDER`：

| 配置 | 管什么 | 支持值 | 实现 |
| --- | --- | --- | --- |
| `AI_PROVIDER` | 生成模型（回答、Wiki、画像、分析） | `demo`/`deepseek`/`openai_compatible`/`local` | Demo 或兼容 HTTP API |
| `RETRIEVAL_PROVIDER` | Qdrant 路径的 Embedding 与 Reranker | `hash`/`qwen` | 哈希与词法，或本机 Qwen |

`hash` 实现是 `HashEmbeddingProvider`，名字叫 `hash-v1`，维度 384（blake2b 分桶 + L2 归一化）；重排是 `LexicalReranker`（`lexical-v1`），用词集合的 Jaccard。设成 `qwen` 才走 `Qwen3-Embedding-0.6B` + `Qwen3-Reranker-0.6B`，这些是本地模型，需要装 `backend[ml]` 依赖，缺依赖会直接报 `RuntimeError` 提示安装命令。

**所以本地 Qwen 作为生成模型要这样配**：`AI_PROVIDER=local` + `AI_BASE_URL` 指向本地 OpenAI 兼容端点 + `AI_MODEL` 填模型名。写作 `AI_PROVIDER=qwen` 是错的——那个值只属于 `RETRIEVAL_PROVIDER`，写在 `AI_PROVIDER` 上会被静默降级成 Demo。

两级重排是检索侧的另一项开关：`RERANK_STAGES_ENABLED=true` 后，粗排（`lexical-v1`）最多挑 15 条送精排。精排（Qwen 或词法）从中挑最多 5 条置顶，分数映射到 `[1, 2]`。其他候选仍保留，默认词法粗排最多给它们 `0.5`，最终返回多少仍由查询上限决定。粗排或精排的评分过程失败时，`CascadingReranker` 改用一轮词法打分。加载模型或依赖失败发生在构建重排器时，会由检索后端的设置决定如何处理。默认关闭时是单级重排。

> **先预测再验证**：把 `AI_PROVIDER` 设成一个不存在的值会怎样？按源码它会回退而不是崩溃——用 `model.provider` 和 `model.model` 确认实际已走 Demo。改配置后务必看 `model` 诊断字段，别只看回答通顺就以为用了新模型。

> 成本相关：`AI_INPUT_PRICE_PER_MILLION` / `AI_OUTPUT_PRICE_PER_MILLION` 用于估算调用成本并记录到模型指标里，按自己的模型价格设置。别把 Key 提交到 Git——`.env` 已被忽略。

## 对照实验：同一句收藏记录的两种导入

[00-2](../00-foundations/00-2-提示词与证据.md) 教过：**收藏只是兴趣线索，不等于会**。这在真实系统里靠一个叫 `preference_signal` 的标记实现——只有作为浏览器互动记录导入时，收藏才会被排除在技能之外。

在同一个默认 Demo 服务上比较两条路线。A 用普通自述，B 用带互动类型的采集快照。分别使用 `demo-experiment` 与 `demo-experiment-favorite` 两个空账号，避免 A 的旧证据混进 B 的画像。

### 实验 A：普通自述文本导入

`POST /api/v1/evidence/text`：

```json
{
  "user_id": "demo-experiment",
  "source_type": "self_statement",
  "source_name": "note",
  "content": "收藏了 Kubernetes 教程"
}
```

然后 `POST /api/v1/profiles/demo-experiment/rebuild`。看画像里**是否出现了 Kubernetes 技能**。

<details>
<summary>预期结果与解释</summary>

默认 Demo 的确定性提取器会按技能别名表命中 `Kubernetes`（别名含 `kubernetes`、`k8s`），把它提成一项技能，而且证据 ID 还指向这条文本。

**为什么？** 因为 `preference_signal` 这个标记只由浏览器采集连接器产生；用 `/evidence/text` 当普通自述导入时没有这个标记，提取器就把它当成「用户自报掌握的技能」。所以默认 Demo 只做关键词演示，不做真实判断。

</details>

### 实验 B：带兴趣标记的导入

工作台的浏览器采集入口会把点赞、收藏和关注标为兴趣线索。可直接用下面的合成快照练习同一后端路径。保存为 UTF-8 的 `favorite.json`，在 Swagger 展开 `POST /api/v1/connectors/browser/import`，`user_id` 填 `demo-experiment-favorite`，`upload` 选该文件。示例 URL 用于通过平台字段校验，整个导入只读取上传的 JSON。

```json
{
  "format": "careerlens-browser-capture-v1",
  "platform": "bilibili",
  "kind": "favorite",
  "source_url": "https://www.bilibili.com/video/BV1CAREER",
  "captured_at": "2026-11-25T00:00:00Z",
  "items": [
    {
      "url": "https://www.bilibili.com/video/BV1CAREER",
      "title": "收藏了 Kubernetes 教程"
    }
  ]
}
```

首次导入应返回 201。先确认 `items[0].source_metadata.claim_strength="preference_signal"`，再调用 `POST /api/v1/profiles/{user_id}/rebuild`，路径填 `demo-experiment-favorite`。画像里应没有 Kubernetes 技能。 [采集快照接口](../../backend/app/api/routes/connectors.py#L17-L48) · [同类导入测试](../../backend/tests/test_connectors_media.py#L196-L221)

<details>
<summary>两个实验的结论</summary>

- 两份输入都包含 Kubernetes。A 交给确定性提取器做别名匹配。B 的标记使提取器先跳过这条材料，因此不会为它新增技能。
- 入门阶段讲「收藏不等于会」，是为了让你先建立正确判断；这里看到 Demo 的误认，是为了让你理解**为什么默认链路只能演示机制**。
- 接了真实模型后，画像提取器还有一条提示词明确说「点赞、收藏、关注仅是兴趣线索」，并会再次用 `preference_ids` 过滤。但那属于模型链路，质量仍需单独验收。

</details>

### 为什么 Demo 会误认：两条防线的源码位置

「收藏不等于会」在真实链路里不是靠一句提示词，而是靠两道独立的过滤。Demo 之所以误认，是因为普通文本导入不带这个标记。

**标记的来源**：浏览器采集连接器把互动分成四类（`published`/`liked`/`favorite`/`following`），只有 `published` 标成 `self_reported_published`，点赞、收藏、关注一律标成 `preference_signal`（`browser_capture.py:92-99`）。用 `/evidence/text` 直接导入时没有这个来源，`source_metadata` 里根本没有 `claim_strength` 字段——提取器自然当它是自述。

**第一条防线（确定性提取）**：`extractor.py:16-19` 遍历证据时，遇到 `claim_strength == "preference_signal"` 直接 `continue`，这类证据完全不进入 skill/target_role 的别名匹配。

**第二条防线（模型提取）**：`llm_extractor.py:50-54` 先把这类证据的 ID 收进 `preference_ids`，然后在 `:78-81` 对 skill/experience/target_role 三类条目，把这些 ID 从 `valid_ids` 里剔除；剔除后为空就整条丢弃。`interest`/`preference` 类不受影响——收藏仍然可以支撑「我对这个感兴趣」，只是不能支撑「我会这个」。系统提示里也明确写了「点赞、收藏和关注仅是兴趣线索」。

两道防线加提示词才构成完整约束。Demo 走确定性提取时没有 `preference_signal` 输入，别名表一命中 `Kubernetes`（别名含 `kubernetes`、`k8s`）就提成技能，于是出现实验 A 的误认。这也解释了为什么 00-2 一开始就强调「收藏只是兴趣线索，不等于会」——它是整条数据链的设计前提，不是一句口号。

## 常见坑

- **把 Key 提交到 Git**：`.env` 已忽略，不要手动加进版本控制。
- **写 `AI_PROVIDER=qwen`**：错，qwen 属于 `RETRIEVAL_PROVIDER`。
