# 08-3 · 参与贡献与结课项目

选一项你亲手验证过的行为，用一组固定输入和一次改动写成结课作品。请另一位读者只看成品就能复跑，再用同样的方式准备一个可复查的 PR。

阅读约 10 分钟，结课动手约 30 分钟。先选一课做过的练习。用过 Compose 或真实模型时，记下实际环境。 [结课模板](../结课模板.md)

**对应源码**：`CONTRIBUTING.md`、`SECURITY.md`、`.github/workflows/`、`scripts/docker-smoke.ps1`、`tutorials/结课模板.md`。

---

## 结课小项目：一页纸说清一件事

用一个合成案例，交付一页纸（Markdown 即可），包含四块：

| 块 | 内容 |
| --- | --- |
| 结论 | 林澈适合什么方向 / 某个岗位匹配结论 |
| 引用 | 每条结论对应的证据 ID，能点回原文 |
| 缺口 | 哪条要求证据不足，明确写「证据不足」 |
| 下一步 | 针对缺口的可执行动作，且对应得上 |

再加两项可复查信息：

- **复现版本。** 记实际使用的代码 tag 或提交 SHA、数据集文件及运行环境。
- **验证结果。** 给出工作目录、命令或接口输入，以及关键输出。实验数据由运行生成时，注明在哪一步取得 ID。

评分看三件事：能否追溯引用、能否区分证据与推测、下一步是否对应缺口。**不按术语数量或报告长短给分。**

> 记住 [08-2](08-2-评测.md) 的边界：不要用 Demo 分数冒充真实准确率；用了合成材料就写明是合成材料。完整的填写模板和一份已填写样例见 [结课模板](../结课模板.md)。

### 为什么还要一个「实验」环节

只写四块结论容易变成「背答案」。教程从头到尾的方法论是**先预测 → 改一个变量 → 看结果 → 解释**，结课项目把这个方法也纳入验收。所以模板里还要求：

| 环节 | 要写什么 |
| --- | --- |
| 固定输入 | 合成材料、JD、画像，写清让别人能复现 |
| 改的一个变量 | 如 `weekly_hours` 6→9、同一段文字换 `source_type`、检索模式 rag→wiki |
| 改之前的预测 | 动手前先写下你以为会发生什么 |
| 实际结果 + 为什么 | 贴关键返回，并指回源码里哪条规则导致这个结果 |
| 一项负例 | 故意制造失败，证明规则真的在起作用 |

**负例是区分「真懂」和「碰巧通过」的关键**。比如 08-2 里收藏卡把 Recall@2 从 1.0 挤到 0.5，就是一个负例——它证明评分确实把那条未标注的证据排进了前两名。再比如 07 的算例从 `valid_ids` 移除 `ev-Python`，分数从 76.5 掉到 56.5，证明匹配真的核对了证据而不只看等级数字。

可复现性也要写清：别人按你给的版本和命令，能不能跑出同样的结果？如果用了真实模型，要说清模型名和版本——模型输出有随机性时，贴出你实际看到的那次结果，并说明哪些部分可能变化。

### 结课结论的四条底线

写完对照这四条自查：

1. **每条结论都能点回 evidence_id，且能追到原文**。不能出现「他说熟悉云原生」却没有对应证据。
2. **区分「证据支持」和「推测」**。做过一个课程项目 ≠ 熟练；收藏过教程 ≠ 会（这是 00-2 和 08-1 反复强调的）。
3. **缺口写「证据不足」，不脑补**。JD 要求 Kubernetes 但没有相关证据，就写证据不足，不要替林澈补一句「大概了解」。
4. **下一步对应缺口**。补缺口的动作要明确做完后会产生什么新证据——比如「完成一次本地 Docker Compose 启动，记录 `docker compose ps`、健康检查结果和环境，再把练习记录作为新证据导入」，而不是「继续学习 Docker」。

这四条其实就是整个教程的三条不变量在结课场景的投影：证据可追溯、写入有边界、数据可收回。评分时看的是判断力，不是篇幅。

## 提交一个可复查的 PR

项目的规矩在 [`CONTRIBUTING.md`](../../CONTRIBUTING.md)，核心是：

1. **一个交付单元一个分支一个 PR**：短期分支，合并后删除，不留长期分支。
2. **PR 描述写清四件事**：学习目标 / 改了什么、在哪个系统和代码版本上测的、验收证据、未验证项。
3. **核对 CI 结果。** Quality Gate 有 `backend-quality`、`frontend-quality` 和 `docker-smoke`。改教程时还要查看 Docsify 的校验工作流。 [质量门禁](../../.github/workflows/quality.yml) · [教程站工作流](../../.github/workflows/docs-pages.yml)
4. **文档改动检查相邻篇章**：改了接口路径、字段、端口，要同步检查教程和配置文档，别留旧写法。
5. **安全漏洞私下报**：按 [`SECURITY.md`](../../SECURITY.md)，不要公开提交。

### 提交前先在本地跑一遍

按你的改动选择本地检查，再在 PR 里记录实测结果。改正文或站内链接时，从仓库根执行 `python docs-site/build.py .cache/course-site` 和 `python -m unittest discover -s docs-site`。改后端时可在已激活的开发环境里复跑下面的 CI 命令。

```bash
# 后端：Ruff 静态检查 + 测试
cd backend
pip install -e ".[dev]"
ruff check --config pyproject.toml . ../examples/tutorials
pytest

# 冻结评测门禁（在 backend 目录）
python -m app.evaluation.cli \
  --dataset app/evaluation/dev_benchmark_v3.json \
  --baseline ../eval/baselines/careerlens-dev-benchmark-v3.json
```

前端在 `frontend` 目录跑 `pnpm install --frozen-lockfile`、`pnpm lint`、`pnpm build`。用 CI 里的 Node 22 命令单独跑浏览器采集与 Run 事件测试，能更快定位对应的交互回归。 [前端检查步骤](../../.github/workflows/quality.yml)`docker-smoke` 用 `docker compose up -d --build --scale worker=2` 起两个 Worker，再跑 `scripts/docker-smoke.ps1` 走一遍真实 PostgreSQL + Qdrant 的主流程和后台任务，CI 使用一次性环境，结束时用 `docker compose down -v` 一并移除卷。本机已有学习资料时，先确认跑的是独立的测试环境，再使用带 `-v` 的清理命令。CI 里的顺序是：前两项 parallel，docker-smoke 等它们过了才跑。

**手工核对也是检查的一部分**：改了接口路径或字段名，就去 Swagger 里确认一次；改了前端样式，就在浏览器里看一眼桌面和手机宽度。CI 证明「代码能跑」，手工核对证明「你改的东西是对的东西」。

### 一条实用的自检清单

提交前问自己：

- [ ] 我改的每句话都能在代码或运行结果里找到依据吗？
- [ ] 我引用的路径 / 字段 / 命令，是照着源码或冒烟脚本核对过的吗？
- [ ] 我有没有把「我测过的」和「我没测的」分开写清楚？
- [ ] 改了接口/字段/端口，相邻教程和配置文档同步了吗？
- [ ] 我有没有贴真实个人资料或密钥？（不要）

**最后一条是硬红线**。本地 Demo 默认不开鉴权，`.env` 也在 `.gitignore` 里，但把真实简历、真实 API Key 粘进 PR 描述或测试用例，就等于把它公开了。教程全程用林澈这个虚构人物和合成材料，就是为了把这条风险挡在源头。

### 安全漏洞怎么报

按 [`SECURITY.md`](../../SECURITY.md)：在私下报告里注明受影响版本，**不要公开开 issue 或提交 PR**。公开披露会让还在用旧版本的人暴露在风险里。这也是「写入有边界」原则在协作流程上的体现——不是所有信息都该立刻公开。

## 从 good first issue 开始

不想一上来就改核心代码，可以先从文档类 issue 入手：修正一个错命令、补一张图、把某个术语解释得更清楚。这类改动风险低、复查快，最适合熟悉流程。

做完第一个 PR，你会体会到这个项目对「可复查」的重视：每个结论要有依据，每个改动要能验证，没验证的要说清楚。这和教程要求你在林澈报告里做的事，是同一种习惯。

## 全教程收尾

到这里你已经走过：

```text
00 看得懂 → 01 跑得通 → 02 建地基 → 03 解析 → 04 检索 → 05 Wiki
        → 06 运行时 → 07 接入验证 → 08 真实模型 / 评测 / 贡献
```

贯穿始终的三条不变量再复习一遍：

1. **证据可追溯**：结论落到稳定 evidence_id，缺证据就报缺口。
2. **写入有边界**：画像修正要确认，Wiki 乐观并发，后台提交与终态同事务。
3. **数据可收回**：导出、删除、清理与补偿是设计的一部分。

这三条不是口号，而是前面每一章里具体机制的抽象：03-A 的两级去重保证出处不丢，05-B 的表格守卫按标识检查行数，05-C 的版本保证改动可追，06 的单事务提交保证状态一致，08-1 的 `preference_signal` 保证兴趣不被当成能力。结课项目和日后的 PR，都是在这三条上继续做。
